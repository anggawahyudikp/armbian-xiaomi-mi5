# First Linux 7.0 boot on gemini

> Historical August 2026 Linux/Ubuntu record. Current installation and load
> rules are in the [flash guide](flash-guide.md) and
> [LK memory audit](bootloader-memory-2026-10-29.md).

2026-08-27. Xiaomi Mi 5 (**gemini**, MSM8996). `fastboot boot` reached Ubuntu with kernel `7.0.0-umeko-rv0-dirty`, USB ACM auto-login, DRM on `msmdrmfb`. The 6.1 boot partition was **not** overwritten on that first attempt.

`--base` must be `0x80000000`. A 7.0 `Image` is larger than umeko's 16 MiB kernel-to-ramdisk gap; ramdisk is at `0x84000000`. USB ACM is kernel `g_serial` (`0525:a4a7`); do not bind a second configfs gadget on the same UDC. ADSP PIL firmware can stall boot; it stays disabled/modular like umeko.

Rescue 6.1 image (gitignored): `inventory/boot-backup/boot-umeko-6.1.14-from-twrp.img`.

## Historical trial sequence and lessons

These August observations predate the October LK binary audit. Their header
addresses are historical, not current packaging instructions. The modern build
uses the audited profile and wrapper rather than trusting header offsets.

| Trial | Change | Observed result |
|---|---|---|
| 1 | Base 0 plus Bluetooth UART earlycon | USB disappeared immediately |
| 2–4 | Restore header base; remove earlycon; disable DRM/EFI | Still no USB |
| 5 | Move ramdisk header to 0x84000000 | Still no USB |
| 6 | Start from umeko config; shrink Image approximately 42 → 25 MiB | Vibration then return to fastboot |
| 7 | Remove panic=10; earlier ACM | No USB after about 48 s |
| 8 | Force peripheral plus nowatchdog | No USB |
| 9 | Disable ADSP/MSS/SLPI | Return to fastboot after about 28 s |
| 10 | Remove tusb320 extcon and nowatchdog | ACM enumerated but no serial data; LK splash remained |
| 11 | DRM on, GPU off; second configfs ACM | ACM still empty, splash unchanged |
| 12 | Match g_serial ownership, enable GPU, include Adreno firmware | Ubuntu, serial and DRM succeeded |

A retained LK splash does not prove Linux never started. Without a DRM modeset,
the last bootloader frame can remain while USB is already functional.

Specific findings:

- `0x7570000` is Bluetooth blsp1_uart2, not the debug console. Actual debug is
  GPIO4/5, blsp2_uart2 at `0x75b0000`, through the unpopulated ISL54062 footprint.
- Unready tusb320l at I2C 0x47 left DWC3 extcon indefinitely deferred. Removing
  extcon and forcing peripheral allowed the UDC to appear in that experiment.
- LK left KPSS watchdog enabled. Linux needed qcom-wdt and
  WATCHDOG_HANDLE_BOOT_ENABLED; `nowatchdog` prevented servicing and led to an
  approximately 28-second bite. `panic=10` could also disguise failure as a
  return to fastboot.
- Early built-in remoteproc tried missing ADSP firmware before USB. Disabling
  ADSP/MSS/SLPI reduced this variable, matching umeko's modular behavior.
- A second configfs gadget competed with built-in g_serial for the UDC. ACM
  enumeration did not establish a working ttyGS0 path. Early nonblocking writes
  before host open could also disappear.
- MSM MDP waited for the GPU component. Disabling GPU left the LK splash.
  pm4/pfp/gpmu loaded, but generic APQ8096 zap returned −5. Fbdev still appeared,
  so full GPU initialization and scanout were distinct results. The actual
  Gemini-signed zap was needed for later acceleration.
- Board IDs matched umeko (`msm-id 0xf6 0x30001`, board31/32). Initramfs had no
  udev-generated by-UUID links, so GPT PARTNAME lookup was necessary. Vibration
  established only drv260x probe, not USB/display readiness.

The first successful boot used four CPUs, mounted old userdata sda15 ext4 rw,
registered S3330/DRV260x, reached systemd245.4 and exposed msmdrmfb/135×120 fbcon.
Subsequent display experiments found built-in MSM/JDI probing could conflict
with the LK splash; modules and delayed userspace loading were preferred.
Adding pshold and mapping IMEM later hung the phone. Removing a userspace
reboot helper did not fix that hang; partition 6.1 remained a useful control.
Never infer hardware reset safety from a different Qualcomm platform.
