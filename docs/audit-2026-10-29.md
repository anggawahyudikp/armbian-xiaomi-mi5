# Mi 5 Armbian audit — 29 October 2026

**Decision at the time: NOT READY TO FLASH as a usable installation.** Userspace
failures were reproduced, boot-time module-index damage was simulated, and USB
configuration contradicted the proposed LAN/storage hub. Reaching part of boot
does not establish a functioning distribution. This is the original audit of
older artifacts; see [subsequent progress](bringup-progress-2026-10-29.md) and
the [latest stability report](stability-progress-2026-10-30.md) for later changes.

Scope: `/path/to/armbian-xiaomi-mi5`, commit
`a54e782431d6dff51c048e3722edd862edbb5467`, release artifacts under `out/`, and
root-ADB inspection of the connected Mi 5. Local kernel: `v7.0`, commit
`028ef9c96e96197026887c0f092424679298aae8`, overlays, release `7.0.0-dirty`.

Phone inspection was read-only: no reboot, flash, formatting, configuration or
partition writes. Implementation/release images were not changed during this
audit. Reports/test artifacts were added under `docs/` and
`out/audit-2026-10-29/`. Historical line numbers below refer to that audited tree.

### A01 — Incompatible rootfs ABI

Debian 12 has glibc 2.36, but overlay binaries/libraries require `GLIBC_2.38`
and even `GLIBC_2.42`: tinfo 6.6, readline 8.3, libnl and wpa_supplicant.

| ARM64 program under QEMU with rootfs libraries | Result |
|---|---|
| `bash --version` | Missing GLIBC_2.42 / GLIBC_2.38 |
| `nmcli --version` | Incompatible readline/tinfo |
| `wpa_supplicant -v` | Missing GLIBC_2.38 |
| `iw --version`, `rfkill --version` | Missing GLIBC_2.38 |
| `NetworkManager --version` | 1.42.4 printed; not a networking test |
| `sshd -V` | Version printed; not a login test |
| `systemd --version` | 252 printed; not a boot test |

Both root/armbian used `/bin/bash`, so shell login/Bash scripts would fail even
if systemd/sshd started. Wi-Fi also lacked a loadable supplicant. Key files
matched byte/hash across `out/rootfs`, ext4, TWRP tar and ZIP payloads: this was
an actual package defect.

Historical root causes: `configure-rootfs.sh` lines 64–67 copied the full overlay;
`build-initramfs.sh` lines 28–30 embedded it; `init.c` lines 291–304/325–330
reapplied it every boot. APT repair alone would be overwritten.

Required fix: distribution-consistent Bookworm arm64 packages, remove
cross-distribution overlay binaries, rebuild rootfs/initramfs/boot/both packages,
and execute core target binaries as a build gate. Do not manually swap glibc.
Local evidence: `out/audit-2026-10-29/userspace-smoke.txt` and
`artifact-validation.txt`.

### A02 — Partial indexes overwrite the complete module tree

Original rootfs indexes resolved `mdt_loader`, `r8152`, `ax88179_178a` and `btqca`.
Historical `build-initramfs.sh` lines 104–135 copied only ten DRM modules,
ran depmod on that subset, then embedded its `modules.dep*`, aliases and other
indexes in the overlay reapplied to rootfs.

| `modprobe -n` request | Before overlay | After overlay |
|---|---|---|
| `mdt_loader`, `r8152`, `ax88179_178a`, `btqca` | Found | Module not found |
| `msm` | Included `mdt_loader` | Dependency absent from plan |

`QCOM_MDT_LOADER=m`; msm requires `qcom_mdt_get_size`/`qcom_mdt_load`. The missing
plan strongly suggests display/GPU load failure. ARM64 modules were not loaded
into the laptop; `-n` only inspected resolution. Keep a complete matched module
set/indexes, or run depmod on the complete final tree before use. Rebuild and
verify initramfs merge. Evidence: `module-overlay-simulation.txt`; original CPIO
metadata matched the simulated staging tree.

### A03 — RAM boot is not automatically nondestructive

The old guide presented `fastboot boot out/boot.img` as harmless to the ROM.
Although fastboot does not flash boot, the loaded program can write storage.
Historical `init.c` lines 362–370 mounted detected userdata as writable **ext4**,
copied the overlay without validating a Debian rootfs, ignored `root=` for an
alternate target, and expected `/sbin/init` there.

This phone used F2FS, so that ext4 mount would fail if reached. On mountable
Android ext4 userdata it could instead write Linux directories into Android.
Provide a separate diagnostic image with its own shell, no writable userdata
and no overlay deployment. Production init must validate filesystem/rootfs
markers before writes and avoid unnecessary fixed-number fallbacks.

### A04 — USB-C hub scenario cannot work with this image

The local DTS forced `dr_mode="peripheral"`, removed extcon and disabled Type-C.
The embedded DTB confirmed this. It cannot host Ethernet/storage in that mode.
Upstream uses USB2 PHY / `maximum-speed="high-speed"`; USB3 and 1 Gbps end-to-end
claims are unsupported. A gigabit adapter link rate is not application throughput.
[Linux v7.0 DTS](https://raw.githubusercontent.com/torvalds/linux/v7.0/arch/arm64/boot/dts/qcom/msm8996-xiaomi-common.dtsi).

Xiaomi's Quick Charge 3.0/Type-C specification does not prove hub USB-PD
pass-through or simultaneous host/charging.
[Xiaomi specifications](https://www.mi.com/in/mi5/specs/).
Choose Wi-Fi plus USB serial initially, or implement/test role switching, VBUS,
a real hub and concurrent charging. Installed drivers alone are insufficient;
RTL8152/AX88179 were modules, not built-in as claimed.

### A05 — ZRAM claimed but not built

Embedded kernel config and `out/kernel/.config` both had ZRAM disabled;
`modprobe -n zram` failed. The old local ZRAM script ignored modprobe failure
and wrote a nonexistent zram0 node. Fixing Bash would not supply kernel support.
Enable ZRAM and its selected algorithm, verify final config and actual
`swapon --show`. Evidence: `out/audit-2026-10-29/embedded-kernel.config`.

### A06 — Battery/UPS protection not established

`mi5-power-guard.sh` tried multiple control nodes including `online`.
The local SMBCHG driver maps `online=0` to `smbchg_usb_enable(false)` /
`USBIN_SUSPEND_BIT`, affecting USB input. Separate charging control was not
exposed through a charge-only node used by the script.

Stopping at 70% while still powered by the adapter was therefore unproven;
input suspension could cause battery discharge/charge cycling. Electrical
behavior needs hardware measurement. Failed capacity reads defaulted to 100%,
failed online reads to 1, and writes ignored errors. Telemetry failure could
hide protection failure. A01 also prevented this Bash daemon from running.

Use the correct charger semantics, read back controls, report failures, and
test adapter loss/restoration and low-battery shutdown. Replace swelling,
zero-downtime and corruption-prevention guarantees with measured limits.
`commit=600` also lengthens journal commit intervals and requires power-loss
assessment.

### A07 — Installer needs preflight before destructive writes

Fastboot packages checked device/rootfs presence but not Gemini identity,
unlock, partition sizes, integrity or boot existence before writing userdata.
The old flash wrapper continued even on wrong product. With mocked fastboot,
a missing boot still reached `flash userdata` before failing on `flash boot`;
the mock offered another product but was never queried. No real fastboot ran.

TWRP already checked product and staged internal ZIP paths in RAM, but ignored
unmount failure and lacked full mount/size/payload validation before format.
Checking only a nonempty extracted boot did not strongly reject partial files.

Validate all payloads, identity, unlock, sizes and a single target before the
first write. Explain Android userdata loss. Verify real backups/recovery.
At audit time `inventory/boot-backup/` contained README files only, not the
referenced recovery images. Evidence: `installer-mock.txt`.

### A08 — Shared SSH identity and default access shipped

The release tar contained RSA/ECDSA/ED25519 host private keys and root/armbian
`authorized_keys`; contents were not printed. Installations would share server
identity and the builder's access. Old rootfs configuration set password `1234`,
passwordless sudo and copied an authorized key from a hardcoded host path.
Root/password SSH and serial autologin were enabled without enforced rotation.

The sanitizer was outside packaging/publishing, created a separate image and
left host keys. Its presence did not sanitize released artifacts. Empty
machine-id was appropriate. Generate unique keys on first boot, keep private
key injection explicit, remove builder access, implement credential onboarding,
and check final packages plus initramfs.

### A09 — TWRP rebuild can retain stale rootfs

Old packaging created `rootfs.tar.gz` only if absent. A rebuild could combine
new boot with old TWRP userspace while Fastboot received the new rootfs.
Regenerate from the validated tree or invalidate by content manifest/hash.
The inspected packages matched at this audit; this finding concerned future
rebuild reliability, not a demonstrated current payload difference.

### A10 — Display/GPU/Bluetooth and auxiliary features incomplete

- Only `a530_zap.*` was present. Adreno also references `a530_pm4.fw`,
  `a530_pfp.fw` and relevant `a530v3_gpmu.fw2`, absent here. GPU acceleration was
  unqualified; this alone does not disprove all framebuffer scanout.
- The static HUD used a no-GLES fallback because a GLES sysroot was unavailable.
  Earlier GPU suspend/rendering results did not validate this build.
- No qca Bluetooth firmware directory, no bootstrap bluez and BT_LE disabled.
  A02 compounded the problem; ready-to-use Bluetooth was unsupported.
- `/mnt/storage` plus udisks2 did not implement headless automount.
- Two `mi5-config` programs in bin/sbin could differ by PATH/sudo. One USB menu
  wrote unused `mi5-usb-mode`; RNDIS service was not enabled and built-in
  g_serial owned the UDC. Mode switching was not a working flow.

Create a firmware manifest, limit claims to tested features, unify configuration,
and test display/blank/resume/network on one matched final image.

### A11 — Custom Debian was not yet a genuine Armbian framework build

The old pipeline built its own kernel and bootstrapped Debian with mmdebstrap/
debootstrap while manually declaring `IMAGE_TYPE=official`, Armbian repository
and version 24.11. Metadata did not prove official support/update provenance.
Until integrated, describe it as Debian 12 arm64 with a custom Mi 5 kernel/overlay.
Matched kernel/DTB/modules/Android-boot distribution updates were not packaged.

Setup accepted existing kernel checkouts without tag verification, could reuse
old `.config`, and did not check every requested fragment value. Historical
Ubuntu dates/success did not validate these Debian packages.

## Recommended order before installation

1. Correct ABI/overlay deployment and module indexes first.
2. Choose realistic USB operation: implement/test host/VBUS/charging for hubs,
   or document USB serial recovery for a Wi-Fi-first server.
3. Enable ZRAM, required firmware and correct charger controls.
4. Fix installer preflight, stale tarballs, credentials and provenance claims.
5. Rebuild a matched set with target-binary, initramfs, module merge, filesystem
   and mocked installer gates.
6. Verify actual backups/recovery; test a diagnostic image that truly leaves
   userdata unwritten. Check unlock in the planned fastboot stage.
7. Only then authorize/install, followed by reboot, resize, login, Wi-Fi,
   display, thermal, charging, shutdown, power-loss and hub/LAN/storage tests.
8. Qualify 24/7 use with the actual long-running workload, kernel logs,
   temperature, network and storage checks; README benchmarks/UPS claims are
   not measured evidence.

## Conclusion limits

This audit did not clean-build everything, install, test mainline drivers on
the phone, stress hardware or measure power. Noninteractive laptop sudo was
unavailable; image inspection, QEMU ARM64 userspace and module-merge simulation
still worked without laptop root. QEMU userspace does not emulate MSM8996 or
prove kernel bootability.

Evidence justified rejecting these packages, but could not guarantee success
after fixes without hardware testing. Boot format, board identity, partition
lookup and package integrity provided a useful foundation; distribution
packaging needed correction before touching Android userdata.
